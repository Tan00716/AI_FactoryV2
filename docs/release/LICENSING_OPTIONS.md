## 1. 第三方依赖许可证概况（实测）

查法：遍历根 `package.json` + 40 个 `packages/*` + 2 个 `apps/*` 的
`dependencies`/`devDependencies`，取全部非 `@ai-factory/` 的外部依赖（共
13 个），再逐个读取 `node_modules/<包名>/package.json` 的 `license` 字段。

| 依赖 | 版本 | 许可证 | 角色 |
|---|---|---|---|
| react | 18.3.1 | MIT | 运行时（随产品分发） |
| react-dom | 18.3.1 | MIT | 运行时（随产品分发） |
| monaco-editor | 0.57.0 | MIT | 运行时（随产品分发） |

| vite | 5.4.21 | MIT | 仅构建期 |
| @vitejs/plugin-react | 4.7.0 | MIT | 仅构建期 |
| electron-builder | 26.15.3 | MIT | 仅构建期（打包工具） |
| @types/node / @types/react / @types/react-dom | — | MIT | 仅构建期（类型声明） |

补充事实：

- **40 个内部包与服务端（apps/server）的运行时外部依赖为零**——只使用
  Node.js 内置模块（`node:http`、`node:sqlite`、`node:crypto` 等）。
- 直接依赖中**没有 GPL / LGPL / AGPL 等 copyleft 许可证**，三条路线在
  依赖层面都不被堵死。
- Electron 内含 Chromium，其开源许可汇总（BSD 等）在 Electron 发行物自带的
  `LICENSES.chromium.html` 中，electron-builder 打包时会随产物带入。
- 无论选哪条路线，**分发时都应随附第三方声明**：MIT 的唯一实质要求是保留
  版权与许可声明文本。建议正式发布时从构建产物生成一份
  `THIRD-PARTY-NOTICES`（含上表 6 个运行时依赖 + Electron/Chromium 声明），
  这是打包步骤，不是决策项。
- 口径边界：上表是直接依赖口径。构建工具的传递依赖只存在于构建机、不随
  产品分发（Electron 本体除外，已计入）；今后每引入一个新运行时依赖，
  应按同样方法复查一次。

## 2. 三条路线对比

| 维度 | MIT | Apache-2.0 | 专有商业许可（EULA） |
|---|---|---|---|
| 能否闭源销售 | 能。许可不要求公开你的源码，拿到代码的人也可合法闭源转售 | 能，同左 | 能，且是唯一路线：源码不公开，按授权条款卖使用权 |
| 源码公开后果 | 一旦公开，任何人可合法复制、打包、免费分发甚至转售，你无法收回 | 同左 | 不公开，无此问题 |
| 专利条款 | 无明示专利授权 | 有明示专利授权 + 专利报复条款（起诉即失去授权），对合作方/企业买家更可预期 | 由 EULA 条款自定，一般不授予专利 |
| 附加义务 | 分发时保留版权与许可声明 | 同左，另需保留 NOTICE（如有）并标注改动 | 由 EULA 自定（授权范围、席位、更新、责任限制等） |
| 商标 | 不授予 | 明确不授予商标权 | 自定 |
| 与「卖软件本体」收入模式的契合 | 差：定价权会被合法转售消解；适合开源引流 + 卖托管/服务/支持 | 差，同左；胜在企业法务友好，适合走开源生态路线时 | 高：按席位/订阅/买断定价都成立，价格与分发完全可控 |
| 生态红利 | 最高（社区贡献、口碑、被集成） | 高，与 MIT 接近 | 无 |
| 法务成本 | 最低（标准文本直接用） | 低（标准文本直接用） | 最高：EULA 需起草并建议律师审阅；买家侧法务审查也更慢 |
| 防盗版/防滥用 | 无从谈起（许可本就允许） | 同左 | 可在 EULA 中约定并配合授权码等技术手段（是否做是另一决策） |

## 3. 每条路线需要 Tan 做的事

**选 MIT**：确认「接受任何人合法转售/免费分发本产品」这一前提；决定后
助手落 `LICENSE`（MIT 标准文本，版权署名需 Tan 确认署名主体，如个人名/
公司名）+ 生成第三方声明，即完成。

**选 Apache-2.0**：同上，另确认是否附 `NOTICE` 文件内容；其余同 MIT。

**选专有 EULA**：
1. 定授权模型：按席位 / 按设备 / 订阅 / 买断（与定价决策联动，见
   RELEASE_CHECKLIST）。
2. 定署名主体与争议解决地等条款要素，找律师起草或审阅 EULA（这一步
   助手不能代劳，只能提供条款要点清单）。
3. 决定是否做授权码/激活等技术执行手段（可后置，不阻塞首发）。
4. 决定后助手落 `LICENSE`（EULA 文本）+ 第三方声明，并从分发物中移除
   源码仓库的公开链接（如适用）。

**混合选项（备查）**：双授权——核心以 MIT/Apache 开源引流，商业版
（安装包/支持/高级功能）以 EULA 销售。需要在开源前就想清楚哪部分开源，
因为开源出去的部分收不回；一般建议先有 EULA 版本打底再考虑。

## 4. 推荐（只推荐，不代选）

**推荐主线：专有商业许可（EULA）。** 理由：

1. 本次目标是「拿出来卖」软件本体。MIT/Apache 一旦公开源码，任何人可
   合法打包转售，定价权在发布当天即被消解——它们是「放弃代码独占、
   换生态与服务收入」的路线，与卖本体的目标直接冲突。
2. 本产品的差异化在可核验的工程治理实现（证据链、审批硬约束、审计
   哈希链），不在社区生态；开源红利对当前阶段的边际价值低。
3. 依赖全是 MIT/Apache 宽松许可（见第 1 节实测），闭源分发无任何障碍，
   唯一义务是随附第三方声明——EULA 路线的依赖成本几乎为零。
4. EULA 的代价（起草/律师审阅）是一次性成本，且可先简后繁；授权码等
   技术手段可后置，不阻塞首发。

若 Tan 判断获客比独占更重要，Apache-2.0 是开源路线里更稳妥的一条
（专利条款对企业买家友好）。**最终选择请 Tan 在 RELEASE_CHECKLIST 的
对应项上拍板；拍板前仓库保持无 LICENSE 的现状即可。**
