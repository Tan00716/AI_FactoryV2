# 已知限制（Known Limitations）

> 对应 SPEC_V2 §55.10：未实现能力明确标记，版本发布说明不把最终产品目标当当前能力。
> 本文档基于 2026-10-11 v2 轮全面测试的真实审计情况编写，不夸大、不隐瞒。

## 运行环境

- **当前仅在 Linux 上验证过**。规格要求的目标环境是 Windows（ENV-L），本机是 Linux，未在 Windows 真机上跑过。
- **没有打过安装包**。electron-builder 配置存在，但从未执行过，没有 `.exe` / `.dmg` 可分发安装包，只能从源码 `npm run dev` / `npm run electron` 启动。
- **Electron 桌面壳从未在真机上点开过**。测试环境无显示器，只验证了 Vite 构建成功，界面交互未做真机冒烟。

## AI 能力

- **除 Codex 外的模型适配器仍是 stub**。CodexAdapter 已真实实现（见下一节），其余供应商（Anthropic 等）未接入，"AI 员工"目前只能经 Codex 这一条真回路干活，且真 turn 尚待登录验证。
- **MCP Registry 有实现，但未接入真实 MCP 服务**。Unknown MCP 默认 BLOCK 的逻辑在，但没有连过真实服务器做握手验证。

## 真实模型接入（Codex app-server）

- **CodexAdapter 已真实现**（2026-10-12，提交 `18fce3c`，SPEC §27/§28 的 B 路线）：一个 JSON-RPC 客户端连接 Codex app-server，双传输——spawn `codex app-server --stdio` 子进程，或连接已用 `--listen ws://` 启动的服务器；走完 initialize → thread/start → turn/start 全流程。线程默认为只读沙箱（sandbox: read-only）+ approvalPolicy `never`，fail-closed 取向，需要写操作时须显式放宽 config。
- **动作映射为 observed actions，toolCalls 恒空**：Codex 在它自己的沙箱里执行命令/改文件/调工具，这些在工厂侧只记为已发生的观测记录（AdapterOutput 新增的 `actions` 字段）；`AdapterOutput.toolCalls` 对 Codex 恒为 `[]`——因为工厂 harness 会把 toolCalls 当待执行指令再跑一遍，塞进去会造成重复执行。反过来，工厂原生工具经 Codex 调用的桥接（如 MCP 转发）尚未实现。
- **真 turn 端到端验证尚未完成**：需先在本开发机完成 `codex login`（device-auth，ChatGPT 授权），当前仍未登录。已实测到认证边界：协议链路对真实 app-server 跑通，`getAccountStatus()` 真实返回 reachable / requiresOpenaiAuth，未登录时 turn 被服务器以真实 401 拒绝，错误原文透传，适配器不回退 StubAdapter、不伪造成功。无登录路径由假服务器 demo（`npm run demo:codex`）与适配器单测覆盖；真机 demo `codex-live.demo.ts` 需要登录，不在 demo 套件内。
- **账号状态（profile）默认仍是 stub**：model-router 的 profile 账号状态默认返回 stub 形状；`getAccountStatus()` 已能经 app-server 真实查询，profile 也已备好 live 注入点（可注入真实结果并标注来源），但 server 侧把真实账号状态接进 API 路由的工作由另一组进行中，尚未完成——接线完成前，API/UI 看到的账号状态仍可能是 stub。
- **StubAdapter 仍是测试与 demo 的默认**：全部单测和 demo 套件（假服务器 Codex demo 除外）都跑在 StubAdapter 的脚本回放上，不消耗真实模型额度。

## 隔离与安全

- **无真实隔离 Host**。在 Linux 本机直跑，非合规隔离后端；`CONFINEMENT_UNAVAILABLE` 的 fail-closed 路径有单测，但真实 Host 隔离未验证。
- Windows 工具探测（PowerShell / .NET 等）未在 Windows 上验证。
- **§36 git evidence 五字段已补齐到证据记录（Batch 21-3，独立复核）**。复核结论：`GitRepo.merge()`/`log()` 计算的五字段与 MergeQueue 落库条目早就是真值，但落到 task 的 merge 证据记录在最后一公里被丢弃（两条合并路由弃用了算好的字段）。本批已接通：`mergeEvidencePayload(pr, fields?)`，直接合并与队列合并的证据记录均含真值五字段（测试钉住 40/64-hex 格式与独立重算）。边界如实：① artifactDigest 对合并/commit 恒为 null——产品尚无"某次变更的构建产物"可绑定（§40 构建 Digest 未与 git 证据面接线），记录的是缺失而非占位；② 外部工具执行的合并走无字段路径，五字段为 null；③ 旧证据不回填；④ code_change 证据的 targetSha 是读取时刻的 HEAD，与 base/candidate 非同一快照语义（已在代码注释写明）。
- **测试/构建双模式口径（Batch 21 主线收口）**：server 源码内部用无扩展名 import（tsc 要求），但 node type-stripping 跑 `apps/server/tests` 时解析不了无扩展名的*值* import——21-1/20-3/21-4 的三个测试文件在稳定树上合并且真实失败（ERR_MODULE_NOT_FOUND、走查 500），已被修：前两个改从编译产物 `../dist/...js` import，走查测试给 server 传入 `FACTORY_SECRETS_DIR` 指向临时目录（否则会继承开发者本地 git-ignored 的 `data/secrets/` 旧 vault，被 fail-closed 解密拒绝——这是产品按设计拒绝，不是产品 bug）。教训已记入仓库级 AGENTS.md：并行子批次的自测数字不算数，主线必须在稳定树上重跑 `node --test apps/server/tests/*.test.ts`。
- **F7 已解决（Batch 22-4）**：`GET /api/tasks/:id/outbox` 的 HTTP 形状 `{from,to,by,at,intent}` 与 DB 列 `outbox_events.event_type`（`WORKFLOW_TRANSITIONED`/`WORKFLOW_FINALIZED`）未对齐——审计发现该列是纯写（`SqliteOutboxStore.append` 用私有 `eventTypeOf(intent)` 写入，`rowToStored` 不读回，没有任何产品代码读取它）。最小诚实修复：`eventTypeOf` 改为导出（列写入规则的单源），`outboxView` 给每个 HTTP 事件加 `eventType: eventTypeOf(e)`（确定性投影、不是第二个存储事实，两面无法漂移）；core 的 `OutboxEvent`/`StoredOutboxEvent` 接口未动。测试钉住：11 步 transition + finalize 后 HTTP 返回 11 个 `WORKFLOW_TRANSITIONED` + 最后 1 个 `WORKFLOW_FINALIZED`，且 HTTP 的 `eventType` 序列与 DB 列逐字一致。
- **Batch 21 独立复核（Batch 22-2）**：四项实质声明全部成立，未发现夸大或造假（报告 `gap-audit/REAUDIT_BATCH21.md`）。唯一修正：可达性矩阵口径为 7/3/6 而非 8/3/5（shell.execute 在目录中标 definition-only 但被服务端接线因而通过门禁）——文档与测试注释已同步修正。
- **§40 → §36 审计结论（Batch 22-3，不接线）**：产品中不存在真实可绑定的构建产物——`lockBuild()` 是纯函数（算构建定义摘要），生产代码零调用方；无 builds 表；合并从不触发构建（queue verify 是候选验证不是构建）；`merge_queue_entries.artifact_digest` 列存在但永远为 null。`artifactDigest` 保持 null + `artifactNote: 'no artifact'` 是当前唯一诚实状态；报告 `gap-audit/AUDIT_BUILD_DIGEST_40_TO_36.md`。前置条件全缺：真实构建执行 → builds 表 → 构建↔candidate↔证据绑定。Batch 23+ 可立项"构建记录最小闭环"。
- **Merge Queue 跨进程 drain 互斥（Batch 23）**：`merge_queue_drain_locks` 表实现 repo 级 drain 租约——同一 DB 文件上多进程同时 drain 同一 repo 时只有一个 drainer；争用方审计 `MERGE_QUEUE_DRAIN_CONTESTED` 后明确让路（不碰队列、不静默双跑、不丢任务，entry 保持 QUEUED 由持锁方处理）；心跳过期后可被接管（`MERGE_QUEUE_DRAIN_TAKEOVER`，接管方先诚实 re-hydrate：终态行不复活，VERIFYING 行降回 QUEUED）；hydrate 在持锁方存活时推迟降级（`MERGE_QUEUE_REHYDRATED_DEFERRED`）；verifier 内失锁则中止合并（`MERGE_QUEUE_DRAIN_LOST`）。租约与 per-entry `tryClaim` 叠加：租约保串行（§36 不变量），entry claim 为纵深（无 drainLock 的旧 backing 仍受 entry claim 保护）。双进程真跑：每 entry 恰好一次。边界：① 只覆盖同一 DB 文件的多进程，不覆盖多机；② 心跳 TTL 默认 2 分钟（`drainLockTtlMs` 可配），verifier 单次超 TTL 无进展会被接管；③ 两进程同时 enqueue 的 position 可能碰撞（无唯一约束），碰撞时顺序不保证、任务不丢；④ entry claim TTL 默认 5 分钟，需大于最长 verifier 运行时间。
- **builds 表已存在但无真实构建（Batch 23）**：`builds` 表（digest、构建定义、revision→commit、SBOM/attestation 引用）已建表，每次合并（直接 + 队列）落一条记录；但合并从不执行真实构建，故记录 `status` 恒为 `'NOT_EXECUTED'`，digest/definition/SBOM/attestation 全为 null 且每个 null 带 pinned 原因注记（记录缺失非占位）。merge 证据的 `artifactDigest` 仍是 null + `'no artifact'`（Batch 22-3 口径不变）。真正闭环还需：真实构建执行 → 状态流转 → digest 回填 → 与证据绑定。
- **§46.2 Secret Broker（Batch 18）**：`packages/secrets` 提供引用式机密存取，服务端只有元数据/写入/删除面，值永不经 HTTP 返回，消费只在进程内（已接两个消费点：`/api/exec` 的 `secretEnv` 注入与 MCP stdio 服务器启动注入 `POST /api/mcp/launch`）。后端强度边界：**file-vault 不是 OS keychain 的等价物**——AES-256-GCM + 机器绑定密钥（HKDF over /etc/machine-id）防的是库文件被拷走/落盘披露；能同时读到 vault.json 与 vault.key（同机同用户或 root）即可解密，本机管理员级攻陷按 §46.1 在保证之外。**OS keychain 后端已建模 + CLI 探测，但开发机无 secret-tool/security 工具，未在真实 keyring 上实测**（仅以 fake runner 钉住 argv/stdin/错误语义）；macOS `security add-generic-password -w` 的值会短暂出现在 argv 中（该 CLI 的已知弱点）；Windows cmdkey 不能读回机密，故不支持。env 后端中机密以明文存在于进程环境，靠部署方保护，仅只读。memory 后端进程退出即失，仅适用于明确配置的 ephemeral 会话。keychain 不可用时选它会让服务拒绝启动（fail-closed），不会静默降级为更弱存储。
- **终端已有真实 PTY（Batch 18，G-11 部分关闭）**。`@ai-factory/runtime` 新增具体 shell 执行实现（`pty.ts`）：pipe 模式（双流分离）与 PTY 模式并存，`createShellTool()` 供 Harness 的 shell 工具按参数 `pty` 逐调用选择；PTY 后端是内嵌的 python3 监督进程（os.openpty + TIOCSWINSZ 预设尺寸 + 子进程独立会话 + 信号转发整树击杀），零新增依赖。命令在 PTY 上看到的是真终端：isatty 为真、窗口尺寸可读回、stdout/stderr 合并为一条终端流、颜色类程序行为与真实终端一致（均有与 pipe 模式的对拍测试钉住）。服务端 `POST /api/exec` 新增 opt-in `pty: true`，与 pipe 路径共用同一套白名单/cwd/控制面目录策略与 §46.2 密钥注入+输出脱敏（不是旁路）。边界如实：① 窗口尺寸在启动时固定，无运行时 resize（SIGWINCH）通道；② 仅 POSIX——Windows 无 POSIX PTY 且 python3 不保证存在，后端不可用时 fail-closed 抛 PTY_UNAVAILABLE，绝不假装终端；③ /api/exec 的 PTY 仍是一次性执行（不转发 stdin、非交互式会话），§50.1 的 Human/AI 独立交互式 Session 由 Batch 19 的会话后端实现，桌面 TerminalPanel 已重接为真会话（见下）；④ PTY 流合并后 stdout/stderr 不可再分开、行尾为终端的 \r\n、输入会被行规程回显，均为真实终端语义而非缺陷。
- **交互式 PTY 会话已落地（Batch 19，§50.1）**。`@ai-factory/runtime` 新增 `PtySession`/`PtySessionManager`：会话经内嵌 python3 监督进程持有真 PTY，控制管道（子进程 fd 3 的 JSON 行）实现真 resize（TIOCSWINSZ + SIGWINCH，`stty size` 可读回；Batch 18 缺的通道已补上）。服务端 `/api/terminal/*`：创建/列表/SSE 流式输出/stdin 写入/resize/关闭；Human 与 AI 为独立 principal，会话间无字节交叉。AI 会话输入按行过门——每完整行须通过与 `/api/exec` 相同的安全策略（拒绝模式+二进制白名单+控制面目录）才进 pty，被拒行丢弃并审计 `AI_LINE_DENIED`；这是与 `/api/exec`「非 human 直接 403」不同的刻意选择（§50.1 要求 AI 会话存在，故用门禁而非一揽子拒绝），逐行近似（heredoc/续行按行判定）不是防恶意模型的安全边界。桌面 TerminalPanel 已从仿真模式重接为真会话（xterm 直连 SSE）。边界如实：① 会话进程内、重启丢失，只留有界归档记录；② 空闲 30 分钟回收、上限 16 会话；③ 控制端猝死（server 被 SIGKILL）时监督进程见 stdin EOF 即整树 SIGKILL 自杀、不留孤儿（有测试钉住）；④ 密钥脱敏按输出块做，跨块拆分的值可能漏网；⑤ 仍仅 POSIX，Windows fail-closed；⑥ 会话 shell 限服务端配置的三个（/bin/bash、/bin/sh、/usr/bin/bash），不接受用户手写启动命令。
- **MCP stdio 启动注入（Batch 19，§46.2 第二消费点）**。`apps/server/src/mcp-launcher.ts`（server 层，未动 packages/mcp 内部——该包本就无 spawner，launcher 建在消费层）：`POST /api/mcp/launch` 启动已安装+启用的 stdio MCP 服务器；`secretEnv {VAR: ref}` 的引用须先在服务器 `credentialRefs` 中声明（未声明 403），再经 Secret Broker 短期租约解析注入子进程 env；值只在启动瞬间存在于进程内存，请求体/日志/审计只出现引用名；stdout/stderr 捕获时即脱敏（与 /api/exec 同一口径）。缺失 ref → 403 且不启动任何进程。租约语义如实：env 在 spawn 时被 OS 复制，rotation 只撤销 launcher 侧租约——运行中子进程保留旧值（`leasesLive=false`、`secretLeaseState='revoked'` 标注，gate verdict 透出标注但不改变放行结论），新启动永远解析最新值，换新机密靠 relaunch。启动表进程内、重启丢失。RBAC：launch/stop 为 admin，列表与脱敏日志为 viewer。边界：**信任流已 HTTP 化（Batch 20，§46）**：`GET /api/mcp/servers/{name}@{version}/trust` 呈现信任评估（从未评估则 assessment 为 null，不冒充）与可执行结论、下一步；`POST …/trust/approve`（admin，仅 BLOCKED 可批，目标策略限 AUTO/AI_REVIEW/HUMAN_APPROVAL）/`…/trust/deny`（记原因、保持 BLOCKED）/`…/trust/revoke`（信任降为 LOW + BLOCKED、卸载、停掉运行中实例）；非法迁移 409、全程审计。launch 对 BLOCKED 的 403 改为 `MCP_TRUST_NOT_APPROVED` 并指向信任端点，不再是死胡同。§34.3 的重审触发靠注册默认值实现：新版本注册即 BLOCKED 须重新审批，不跨版本继承。revoke 停掉运行中实例是本地 fail-closed 决定（规格未明令）。**注册表与信任已落库（Batch 21）**：`mcp_servers`（注册全字段 + 信任等级/策略 + 评估 JSON）与 `mcp_installs` 表写透；注册/握手协商/健康检查/历史追加/评估/安装/卸载全部经持久化接缝（`McpRegistrySink` + manager 观察者，包层保持 storage-agnostic）；服务端启动时水合（不产生新历史/审计事件——水合是得知，不是重做），已批准的服务器重启后保持信任（e2e 钉死：注册→approve→SIGKILL→重开→launch 201）。健康是时点数据：水合时标记 stale 且不装入 live 注册表，重启不伪装成刚查过；launches 仍进程内（Batch 19 口径）。机密防护：`credentialRefs` 只存引用名，且 `runtimePolicy.stdioEnvFixed` 的值在落库前被剥离（键保留），哨兵值全字节扫描钉住落盘。边界：多进程同时写同一 DB 文件的并发语义未做（单实例假设，与 merge queue 同口径）；腐坏行跳过并打日志，不阻断启动。规格 §34/§46 无"重启后保持信任"的明文 MUST——这是按可售耐久做的缺口关闭，非规格要求。

- **Git Broker 与 Merge Queue（§36，Batch 16；队列已落库，Batch 20）**。候选验证缺省只查冲突，不自动跑项目测试套件（除非注入验证器）；**队列与 PR 记录已持久化**（`pull_requests` / `merge_queue_entries` 表）：每次变更即时写透，重启后 hydrate() 重建——崩溃时卡在 VERIFYING 的条目诚实降回 QUEUED 待重验（记 `MERGE_QUEUE_REHYDRATED` 审计，旧验证结论只作展示，重验必重新组装候选）、MERGED/FAILED 保留为历史；同一 PR 的活跃条目唯一性由部分唯一索引跨进程保证；决策审计引用（decisionAuditRef）指向终端决策事件的审计 id。**仍未做**：多进程同时排空同一 repo 队列的并发语义（两个进程可能各自 hydrate 后重复处理同一条目，生产部署应保持单实例或外部串行化）；队列运行态对象本身仍是进程内内存（靠落库重建）。

- **服务端已有角色权限（RBAC，Batch 15）**。在原单 token 门之上新增三档角色：viewer（只读 GET）、operator（日常写：任务/证据/流转/run/审批）、admin（高危面：backup/restore/备份清单、retention 策略与 legal hold 与 enforce、policy 写、自治等级）。配置 env `FACTORY_API_TOKENS`（逗号分隔 `role:token`；格式错误启动即拒绝且不回显 token）。**向后兼容**：不设该变量时行为与从前一致——单 `FACTORY_API_TOKEN` 即 admin 全权；两者都不设且 loopback 绑定时仍是本地免门模式（有效角色 admin），非 loopback 无凭据仍拒绝启动。角色不足返回 403 并写 `RBAC_DENIED` 审计（记角色不记 token）；`GET /api/auth/whoami` 返回调用方自身角色与认证模式，桌面顶栏据此显示当前角色/本地模式。边界：这是单机共享密钥式的粗粒度角色，不是多用户账号体系（无逐人身份、无令牌轮换/吊销面）；桌面仍用同一个本地 token 槽位，多角色令牌靠运维分发。
