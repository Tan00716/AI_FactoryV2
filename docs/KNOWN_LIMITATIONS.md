- **Merge Queue 跨进程 drain 互斥（Batch 23）**：`merge_queue_drain_locks` 表实现 repo 级 drain 租约——同一 DB 文件上多进程同时 drain 同一 repo 时只有一个 drainer；争用方审计 `MERGE_QUEUE_DRAIN_CONTESTED` 后明确让路（不碰队列、不静默双跑、不丢任务，entry 保持 QUEUED 由持锁方处理）；心跳过期后可被接管（`MERGE_QUEUE_DRAIN_TAKEOVER`，接管方先诚实 re-hydrate：终态行不复活，VERIFYING 行降回 QUEUED）；hydrate 在持锁方存活时推迟降级（`MERGE_QUEUE_REHYDRATED_DEFERRED`）；verifier 内失锁则中止合并（`MERGE_QUEUE_DRAIN_LOST`）。租约与 per-entry `tryClaim` 叠加：租约保串行（§36 不变量），entry claim 为纵深（无 drainLock 的旧 backing 仍受 entry claim 保护）。双进程真跑：每 entry 恰好一次。边界：① 只覆盖同一 DB 文件的多进程，不覆盖多机——多机脑裂场景与方案对比见 `docs/merge-queue-multimachine.md`（Batch 46 设计文档）：两机各用各的 DB 文件时租约/claim/唯一索引全部按库生效，两边都会 drain（§36 不变量破、同一 PR 可能被合并两次、审计链分叉）；共享 SQLite 文件走 NFS 已知不可行（文件锁不可靠）；时钟偏移会导致过早抢锁或锁停滞；git 仓库本身也在本地磁盘，是锁解决不了的另一维。只换分布式锁不动状态是伪方案（"写到哪"比"谁先写"更根本）；真解是共享数据库（Postgres，前置"远程 DB 驱动"本身是硬阻塞）或明确不支持多机。部署建议：merge queue 只跑单实例；② 心跳 TTL 默认 2 分钟（`drainLockTtlMs` 可配），verifier 单次超 TTL 无进展会被接管；③ **enqueue position 跨进程碰撞已关闭（Batch 26）**：此前两进程同时 enqueue 同一 repo 会算出相同 position（真跑复现：两条目同落 position 2）。现 `(repo_path, position)` 唯一索引为仲裁者——碰撞时重读 backing 真实 max 重试（最多 8 次，审计 `GIT_MERGE_QUEUE_POSITION_RETRY`，永不静默丢任务）；老库在迁移中先确定性修复已存在的碰撞再建索引。边界：仍只覆盖同一 DB 文件的多进程；PR 重复入队仍走原 409 口径（已与位置碰撞区分，不再混淆）；④ entry claim TTL 默认 5 分钟，需大于最长 verifier 运行时间。
- **构建执行已真实落地（Batch 24-2）**：`builds` 表 + 每次合并落记录（Batch 23）之上，merge 成功后按显式运维配置 `FACTORY_BUILD_COMMAND` 在 `git worktree add --detach` 钉住 revision 的干净工作区中真实执行构建（后台 FIFO 串行 runner，fire-and-forget 不阻塞 merge 响应）；走与 `/api/exec` 完全相同的命令策略（deny patterns + 二进制白名单 + 控制面目录守卫）；超时 `FACTORY_BUILD_TIMEOUT_MS`（默认 10 分钟）杀整个进程树；成功失败都删工作区。digest = `lockBuild(definition)` 的真实重算：revision=真实 candidate SHA、lockfileHash=工作区真实 lockfile 的 sha256（缺失则缺项点名）、toolchain=真实执行环境（`node <ver> <platform>-<arch>`，可覆盖）、buildDefinitionHash=sha256(命令)、configHash=配置真实文件哈希；任一必填输入缺失 → digest 保持 null 并点名缺失项。成功→`markSucceeded` + `BUILD_SUCCEEDED` 审计；digest 为真时回填 merge 证据的 `artifactDigest`（`'no artifact'` 注记移除）；失败/超时/策略拒绝→`markFailed` + `BUILD_FAILED`。未配置 `FACTORY_BUILD_COMMAND` = 功能关闭，记录保持 `NOT_EXECUTED`。关键边界：构建命令执行仓库控制的代码——**Batch 37 起默认进 bubblewrap 沙箱**（只读 `/usr`、`/opt`，唯一可写绑定工作区→`/work`，网络默认隔离；bwrap 不可用时审计 `SANDBOX_UNAVAILABLE` 并诚实回退），但"只对信任仓库启用"的运维姿态不变；SBOM 有 retention；attestation dev 路径已关闭（Batch 38：FACTORY_ATTESTATION_KEY + in-toto dev 签名）并纳入 retention（Batch 39）；生产签名等 Tan 的密钥决策；多机/分布式构建未做（进程内 runner）。
- **构建 SBOM（Batch 25）**：构建成功后、工作区删除前，从工作区 lockfile 派生 CycloneDX 1.5 精简 SBOM（声明/解析依赖清单，provenance 写进文档——不是安装树扫描，不是产物链接证明），落盘到 `FACTORY_SBOM_DIR`（默认 `<cwd>/data/sboms`），`sbomRef` 指向该文件。支持 package-lock.json（v1/v2/v3）、yarn classic、pnpm-lock.yaml、Cargo.lock，其余 lockfile 大声 skip；去重 + 确定性排序 + 上限 20000（超了截断并明示）；无可用 lockfile 或生成失败时 sbomRef 为 null 并点名原因，构建本身不受影响（记录保持 SUCCEEDED）。边界：sbomRef 为本机绝对路径（DB 搬家不带 sboms 目录即悬空，跨机不移植）；**构建只读面已关闭（Batch 31，walkthrough F9）**：`GET /api/builds`（列表：status/prId/revision 过滤，limit/offset 分页）与 `GET /api/builds/:id`（单条）只读面已上线，viewer 可读；只处理 GET（其他方法 405），只读记录拷贝原样序列化（null 字段不编造，note 字段恒存在）。真 server e2e：merge → 真实构建 → 纯 HTTP 轮询 `/api/builds/:id` 观察到 SUCCEEDED。边界：记录是 insert-only 历史，状态机单向（终端行不可改写）。
